Why do we need multithreading in Java?

Definition: A thread is the smallest unit of execution within a process. Multithreading allows a program to perform two or more tasks concurrently within the same process, sharing the same memory space.
Reason 1

Better CPU utilization

Idle CPU time (e.g., waiting for I/O) is used by other threads instead of being wasted.

Reason 2

Responsive applications

UI thread stays free while background threads handle network calls, file reads, or computations.

Reason 3

Parallel processing

Multi-core processors can execute threads truly simultaneously, cutting task completion time.

Reason 4

Simplified modeling

Real-world tasks (e.g., producer/consumer, client/server) map naturally onto separate threads.

Reason 5

Resource sharing

Threads share process memory, making data exchange cheaper than inter-process communication.

Reason 6

Scalability

Server applications spawn a thread per client request, handling thousands of users concurrently.

How to implement multithreading in Java

Java provides two primary ways to create threads. Prefer Runnable over extending Thread — it keeps inheritance free and enables lambda syntax.

Way 1 — extending Thread Thread.java
class MyThread extends Thread {
    @Override
    public void run() {
        for (int i = 1; i <= 5; i++) {
            System.out.println(
                Thread.currentThread().getName()
                + " → " + i);
        }
    }
}

public class Main {
    public static void main(String[] args) {
        MyThread t1 = new MyThread();
        MyThread t2 = new MyThread();
        t1.start(); // starts new thread
        t2.start();
    }
}
Way 2 — implementing Runnable Runnable.java
class Task implements Runnable {
    @Override
    public void run() {
        for (int i = 1; i <= 5; i++) {
            System.out.println(
                Thread.currentThread().getName()
                + " → " + i);
        }
    }
}

public class Main {
    public static void main(String[] args) {
        Thread t1 = new Thread(new Task());
        Thread t2 = new Thread(() ->
            System.out.println("Lambda thread"));
        t1.start();
        t2.start();
    }
}
Way 3 — ExecutorService (recommended for production) Executor.java
import java.util.concurrent.*;

public class ExecutorDemo {
    public static void main(String[] args) {
        ExecutorService pool = Executors.newFixedThreadPool(3); // 3 threads

        for (int i = 1; i <= 6; i++) {
            int taskId = i;
            pool.execute(() ->
                System.out.println("Task " + taskId + " on " +
                    Thread.currentThread().getName()));
        }
        pool.shutdown(); // no new tasks; waits for running tasks to finish
    }
}
Key methods: start() creates a new OS thread and calls run() asynchronously. Calling run() directly executes it on the current thread — no concurrency.

Synchronization

Problem — Race condition: When two or more threads access a shared variable concurrently and at least one modifies it, the result depends on thread scheduling — producing incorrect, unpredictable output.

❌ Unsafe — race condition

No synchronization Unsafe.java
class Counter {
    private int count = 0;

    public void increment() {
        count++; // read-modify-write
                 // NOT atomic! 3 ops.
    }

    public int get() { return count; }
}
// Expected: 2000, Got: 1743 (data loss)

✔ Safe — synchronized

synchronized method Safe.java
class Counter {
    private int count = 0;

    public synchronized void increment() {
        count++; // only one thread at a time
    }

    public synchronized int get() {
        return count;
    }
}
// Expected: 2000, Got: 2000 ✓
synchronized block (finer-grained) + ReentrantLock alternative Sync.java
import java.util.concurrent.locks.*;

class FineGrained {
    private int count = 0;
    private final Object lock = new Object();

    public void increment() {
        synchronized (lock) { // only locks this block, not the whole object
            count++;
        }
    }
}

class LockDemo {
    private int count = 0;
    private final ReentrantLock lock = new ReentrantLock();

    public void increment() {
        lock.lock();
        try {
            count++;
        } finally {
            lock.unlock(); // always unlock — even on exception
        }
    }
}
volatile keyword

Visibility — not atomicity

Declares a variable as always read from main memory, not a thread's local cache. Use for flags (boolean running) — not for compound operations like count++.

Atomic classes

Lock-free thread safety

AtomicInteger, AtomicLong from java.util.concurrent.atomic use hardware CAS instructions — faster than locks for single-variable operations.

Bank account withdrawal — problem & solution

Scenario: Two ATM threads simultaneously withdraw ৳800 from an account with ৳1000 balance. Without synchronization, both threads pass the balance check before either deducts — the account goes negative.

❌ Problem — race condition on balance

Unsafe withdrawal BankUnsafe.java
class BankAccount {
    private int balance = 1000;

    public void withdraw(int amount) {
        if (balance >= amount) {
            // ATM-1 checks: 1000>=800 ✓
            // context switch here!
            // ATM-2 checks: 1000>=800 ✓
            balance -= amount;
            // Both deduct → balance = -600!
        }
    }
}

✔ Solution — synchronized method

Safe withdrawal BankSafe.java
class BankAccount {
    private int balance = 1000;

    public synchronized void withdraw(int amount) {
        if (balance >= amount) {
            System.out.println(
                "Withdrawing: " + amount);
            balance -= amount;
            System.out.println(
                "Balance: " + balance);
        } else {
            System.out.println(
                "Insufficient funds!");
        }
    }
}
Complete runnable example BankDemo.java
public class BankDemo {
    public static void main(String[] args) {
        BankAccount account = new BankAccount(1000);

        Thread atm1 = new Thread(() -> account.withdraw(800), "ATM-1");
        Thread atm2 = new Thread(() -> account.withdraw(800), "ATM-2");

        atm1.start();
        atm2.start();
    }
}
/* Output (synchronized):
   ATM-1 → Withdrawing: 800 | Balance: 200
   ATM-2 → Insufficient funds!              */
Root cause: The check-then-act sequence (if balance ≥ amount → deduct) is a compound operation. It is not atomic. The CPU can switch threads between the check and the deduction.
Fix: synchronized acquires the object's monitor lock. The entire check-then-deduct block becomes indivisible — no other thread can enter until it completes.

Observing thread states LifecycleDemo.java
public class LifecycleDemo {
    public static void main(String[] args) throws InterruptedException {
        Thread t = new Thread(() -> {
            try { Thread.sleep(500); }
            catch (InterruptedException e) {}
        });

        System.out.println(t.getState()); // NEW
        t.start();
        System.out.println(t.getState()); // RUNNABLE
        Thread.sleep(100);
        System.out.println(t.getState()); // TIMED_WAITING
        t.join();
        System.out.println(t.getState()); // TERMINATED
    }
}
sleep(ms)

Pause execution

Pauses the thread for the specified time. Does not release any monitor locks.

join()

Wait for completion

Calling thread pauses until the target thread finishes. Used to sequence thread results.

interrupt()

Request cancellation

Sets the thread's interrupt flag. The thread should check isInterrupted() and stop gracefully.

wait() / notify()

Inter-thread communication

wait() releases the lock and sleeps; notifyAll() wakes all waiting threads. Must be called inside synchronized.

setPriority(n)

Thread priority

1 (MIN) to 10 (MAX), default 5 (NORM). Hints to the scheduler — not a guarantee of execution order.

setDaemon(true)

Daemon threads

Background service threads (e.g., GC). JVM exits when only daemon threads remain — they don't prevent shutdown.

Module project ideas

Project 1 — Multithreaded ATM Simulation

Recommended · Core concepts · 2–3 weeks

Build a simulation of multiple ATM terminals accessing a shared bank. Implement withdrawal, deposit, and balance check operations. Demonstrate race conditions with unsynchronized code, then fix using synchronized or ReentrantLock. Add a transaction log using a thread-safe queue.

Synchronization ReentrantLock Race Conditions Thread Safety

Project 2 — Producer–Consumer Message Queue

Intermediate · Pattern design · 2–3 weeks

Simulate a message broker where multiple producer threads generate log entries and multiple consumer threads process them. Implement a bounded buffer using ArrayBlockingQueue. Track throughput and demonstrate backpressure when producers are faster than consumers.

BlockingQueue ExecutorService Design Pattern Bounded Buffer

Project 3 — Parallel File Word Counter

Applied · Real-world · 2–3 weeks

Given a directory of text files, use a thread pool (ExecutorService) to count words in each file in parallel. Merge results into a ConcurrentHashMap. Compare wall-clock time against single-threaded implementation and report speedup.

ExecutorService ConcurrentHashMap Future / Callable Performance
